# 输入 State / Sequence 方案与时间窗口调研

状态：用户已批准执行，`FrameWork` 已完成本方案的源码与编辑器，源码已本地提交于 `d3785413`；Manager Prefab 与文档另行提交，7 个普攻资产的迁移及用户后续测试调整仅留在本地，不纳入提交。推送已停止，尚未确认成功。三组源码编译及 77 个选定纯逻辑用例通过，用户反馈输入与编辑器手工测试未发现问题；**完整 Unity 原生集成、设备覆盖及 Player 验收仍待做**。本页保留设计理由、实施步骤和验收清单，当前精确行为见 [输入实现合同](Player_Input_Contract.md)。

## 已确认的规则

- 输入 StateCondition 检查当前状态；输入 SequenceCondition 只包含 Event Clip，不混入 State，不嵌套事件当时的状态要求。
- 单个按钮事件也是有效 Sequence，普通普攻不必配置多个步骤。
- Sequence 支持按钮按下/松开，以及识别层产生的方向进入/回中事件。
- 方向招式相对于有效锁定目标：朝向目标为前，背离为后。无有效锁定目标时，不匹配这类方向招式；普通按钮操作和移动不因此被禁用。
- 第一版采用四主方向及回中，斜输入归最近主方向，边界采用稳定的容差处理，不因轻微抖动生成重复进入事件。
- Sequence 允许夹杂其他记录，检查所需事件的先后顺序和允许的时间跨度，不要求事件紧邻。若要求显式回中，就在序列里填写回中事件。
- State 只检查判定时的状态，不自动绑定历史攻击时刻；外层 State 与历史 Sequence 组合时，接受这一明确语义。
- 匹配只读，结果归本次角色、本次候选；落选不消费，真正开始成功后才消费。
- 特殊招式因地面/取消规则不满足时，合法普攻仍可参与原有仲裁；不通过提前吃输入来决定优先级。此约定不等于新增“实际 Begin 失败后自动重试另一候选”的机制。
- 更换角色、禁输入及失焦清理历史。锁定目标/参考基准改变时，不拿旧基准下的方向事件拼接新序列；不应因此擅自清掉无关的普通按钮请求。

## 方案复核：实现前必须补齐的合同

### 1. 方向解释与实际移动使用同一套坐标规则

当前源码中，PlayerInputController 的锁定键消费后调用 ToggleSoftLock；PlayerLocomotionIntentResolver 仅在 HardLock 下采用目标相对移动，其他情况下主要使用相机相对移动。**不能把摇杆上直接当作“朝向锁定目标”。**

- 方向识别应复用现有移动方向转换：先确定输入对应的世界方向，再判断它相对目标是前、后、左、右。不能独立复制出另一套不一致的移动规则。
- 不为实现招式识别擅自改变软锁/硬锁或相机行为。有有效锁定目标时按目标相对方向解释；普通按钮和移动仍走原路径。
- 原始移动记录不依赖 Actor/目标/招式。坐标解释留在识别层；识别结果必须保留其时间、来源身份及方向参考会话，不能每次查询用最新相机/角色姿态重解释旧记录。
- State 可以读取当前方向；方向 Event 必须由真实输入变化产生。保持摇杆时，目标移动或镜头旋转不能凭空生成一次新的方向进入。
- 换锁定目标、丢失目标或切换方向参考规则时，使旧方向匹配失效。已有按钮请求不因此全部清空；恢复锁定也不能把原本按住的方向伪造成新操作。
- **本轮落实的采样点**：固定输入发布、处理 Lock 按下之后采样一次，该批新移动变化共用此基准；保留原始输入时间/身份，但不宣称还原设备事件时刻的世界姿态，不新增世界姿态回放系统。
- 新方向参考只建立当前轴基线，当步已发布的操作不补认成新参考下的方向命令；建议先锁定，再做方向序列。方向序列也不能借用新参考建立前的按钮记录，普通按钮序列则不受影响。
- ActorCombater 增加非序列化 LockRevision，只观察状态/目标改变及组件停用。即使同一步解锁又锁回同一目标，也能切断方向历史；不改变原锁定/选敌行为。

### 2. 方向历史、事件与当前状态分工

- 实施前 Buffer 虽有待处理移动队列，但只留下最新 Move；本轮已补有限长度、带原始时间和稳定顺序的移动变化记录。
- 按钮与移动变化必须有可比较的顺序；相同时间戳保留确定的采集顺序。不能按事件类别重排，也不能要求每个 Clip 至少间隔一个固定 Tick。
- 方向识别只在分类发生真实变化时产生进入/回中事件；保持方向不重复产生事件，数值抖动不等于重复进入。
- 历史清理与当前状态独立：旧的“进入前”过期，不意味着当前摇杆回中；消费方向事件也不改变移动状态。
- 死区、方向边界和容差归识别规则，优先解决边界反复跳变，不靠固定延迟几帧掩盖问题。

### 3. 历史保留、匹配和消费必须一起调整

实施前 PlayerInputBuffer 在事件超过 0.2 秒后删除记录，CanConsume 也要求每条事件都没有超过 BufferSeconds。**本轮已同时调整历史保留和组内截止时间；单事件规则不能原样用于多步序列，不能只扩大历史列表而不修改消费校验。**

例如 0.00 后、0.25 前、0.45 攻击：在 0.45 检查时，整段合法，但第一步已经超过 0.2 秒。新的有效性规则应为：

- 整组事件属于正确 owner/输入会话；涉及方向时还属于有效的方向参考会话。
- 每条匹配事件仍存在、未消费，身份和顺序有效；整段跨度满足该 Sequence 的配置。
- **仅终端事件额外受 0.2 秒出招缓存限制**，不能要求前面的上下文步骤也发生在最近 0.2 秒内。
- 匹配阶段和成功后消费阶段遵守同一套规则；不能出现“判定有效，却因为旧的单事件时效检查而拒绝消费”。凭据仍绑定本次候选及固定 Tick，不能跨 Tick 直接复用。
- 第一版成功后原子消费全部匹配事件，不消费夹杂的无关记录，不改变按住状态或 Move。避免同一段“后 -> 前”反复配上新的攻击而连续触发特殊招式。
- 落选、准入失败、开始失败均不消费；消费前先验证整组，失败不能只吃其中一部分。
- 保留当前的生命周期安全原则：Begin 期间发生清理/换角色时，旧凭据失效，绝不误消费新会话输入。

### 4. 宽松匹配仍有严格的正确性边界

- 所需事件按时间及稳定顺序依次发生；一个事件不能满足两个 Clip。
- 连续两个相同方向 Clip，需要两次真实进入该方向，不能用持续保持状态凑数。
- 允许夹杂其他事件，不等于允许跨会话、跨已消费记录或超时拼接。
- 存在重复事件和多个可能起点时，匹配器必须能找到合法组合，不能因为一次错误的贪心选择而漏掉有效序列。多组都合法时采用明确、稳定的选择顺序。
- 重复检查历史不产生新事件身份、不更新时间，也不延长请求有效期。
- 特殊招式与普通攻击共享终端按钮事件时，仍由现有优先级与取消规则仲裁，不让 Sequence 提前占用输入。

### 5. 配置含义与误触风险必须明确

普通方向攻击与方向进入序列不是同一件事：

```text
当前推着前就能发动：
  State：当前方向为前
  Sequence：攻击按下

要求最近刚进入前方向再攻击：
  Sequence：进入前 -> 攻击按下
```

前者允许已经向前移动较长时间后按攻击；后者要求方向进入事件仍在序列窗口内。编辑器名称和说明必须体现区别，不能把“当前为前”写成“进入前”。State 与缓存攻击的组合仍按已确认的当前状态语义执行，不偷偷改成事件快照检查。

默认 0.5 秒且允许夹杂事件，有可能把“后退走位 -> 向前移动 -> 普通攻击”识别成特殊招式。**验收不仅看想出招时的成功率，还要看正常走位时的误触率。** 若误触偏多，先按实际招式缩短可配置窗口、检查方向阈值和动作配置，不立即增加一批隐藏识别规则。

## 默认时间的结论

InputSequenceCondition 已暴露 **Max Sequence Time（整段完成时间）**，默认 **0.5 秒真实时间**，每个 Sequence 可以配置。第一版支持 **0～2 秒**，超出范围或非有限配置拒绝，避免窗口超出可保留上下文而静默漏识别。

定义：最后一个匹配事件的发生时间减去第一个匹配事件的发生时间，不超过此值。

```text
Sequence：进入后 -> 进入前 -> 攻击按下

0.00 后，0.12 前，0.28 攻击：通过
0.00 后，0.30 前，0.50 攻击：通过（包含边界）
0.00 后，0.30 前，0.60 攻击：默认不通过；将窗口改为 0.7 可通过
```

- 0.5 秒在 60 Hz 下相当于 30 个逻辑帧，仅用于理解；实现仍比较原始实时事件时间，不能按渲染帧累加。
- 第一版只暴露这个序列时间参数，不额外增加一个默认也生效的步间隔开关，以免配置者混淆总时限与每步时限。若以后有明确的逐步精确窗口需求，再单独设计。
- 单 Event 序列的跨度为零，但终端事件仍受出招缓存约束，不能凭此永久有效。
- 默认值是为当前轻量方向命令选择的试手感起点，**不是经官方证实的 DMC / Bayonetta 内部参数，也不是所有成熟 ACT 的统一标准**。

### 不得与出招缓存混淆

| 参数 | 含义 | 本项目安排 |
| --- | --- | --- |
| Sequence 完成时间 | 完成整段输入允许多久 | 每个 Sequence 可调，建议默认 0.5 秒 |
| 单步间隔 | 相邻步骤之间允许多久 | 第一版不额外引入独立参数 |
| 出招缓存 | 最后操作发生后，请求还能等多久 | 保留现有默认 0.2 秒，独立于序列窗口 |

例如第一步在 0.00、最后攻击在 0.40：序列跨度 0.40；在 0.55 检查时，终端请求年龄是 0.15，仍可参与；在 0.65 检查时，终端年龄 0.25，已经过期。不是从第一次识别成功开始重新计时，也不因反复匹配而续期。

方向/按钮历史必须覆盖支持的序列窗口加终端缓存；本轮按支持上限保留 **2 秒上下文 + 当前终端缓存**，默认约 2.2 秒，不为每个条件再配置历史时长。不能在 0.2 秒时删掉所有上下文，也不能静默接受超过支持上限的 Sequence。记录过期与当前 held/Move 独立。时间比较只加一微秒数值误差余量，处理 float 配置和 double 时间边界的表示差异，不用作额外手感窗口。

## 公开资料及证据边界

### 1. PlatinumGames 官方 Bayonetta 2 开发博客

[小ネタとかいろいろ](https://www.platinumgames.co.jp/dev-bayonetta2/article/668)，第 3 节说明铁山靠使用摇杆后、前，再按 P 的命令。

能支持：成熟 ACT 确有当前需要的简单方向命令。

不能支持：该文章未公开识别窗口数值，不能据此宣称 Bayonetta 使用 0.5 秒。

### 2. DMC5 的实际操作讨论

[GameFAQs: Doing those back to forward attacks](https://gamefaqs.gamespot.com/boards/241018-devil-may-cry-5/77602180)，第 9 楼玩家描述保持锁定、在半秒内完成后到前再攻击，能够稳定执行。

能支持：0.5 秒量级可以作为这种操作的人类执行节奏参考。

不能支持：这是玩家经验，不是开发者说明或受控测量，无法证明游戏内部最大允许窗口恰好等于 0.5 秒。执行一次成功也不能测出上限。

### 3. Unreal Enhanced Input 官方 API

[InputComboStepData — Unreal Python 5.6](https://dev.epicgames.com/documentation/en-us/unreal-engine/python-api/class/InputComboStepData?application_version=5.6)，time_to_press_key 定义为上一步完成后，按下一步的允许时间，第一步忽略该值。

能支持：组合识别的步骤时限应有明确起止点和可配置语义。

不能支持：它是通用引擎 API，不是某款 ACT 的参数，也不能把它的逐步时限当成我们的整段窗口。该页面没有给出可用作 ACT 统一默认的 0.5 秒证据。

### 4. Game Creator 商业近战框架文档

[Melee / Input](https://docs.gamecreator.io/melee/input/)，Input Buffer 节写明其默认缓存窗口为 0.5 秒，且可修改。

能支持：近战输入系统中存在可配置的半秒级宽容设置。

不能支持：它说的是提前输入缓存，不是“后 -> 前 -> 攻击”的整段识别窗口。因此不把这条数值移植到本项目缓存，也不将其当成 Sequence 默认值的直接测量证据。

### 5. 动作游戏社区对缓存的说明

[DmC Input Buffering](https://devilmaycry.fandom.com/wiki/Input_Buffering)，Buffering Windows 节指出不同攻击的接受窗口有所区别。

能支持：实际动作系统不能用一个数字概括所有招式的缓存规则。

不能支持：这是社区资料，且没有给出本项目所需的方向序列精确时间。不能拿取消/恢复动画窗口冒充命令完成时间。

### 调研判断

已检索中英文及日文的 DMC / Bayonetta 方向命令、输入窗口及帧数据资料，并交叉检查官方开发博客、通用引擎 API、商业框架文档和玩家讨论。**未找到足够可靠的公开证据，证明所有成熟 ACT 采用同一个序列宽容时间。**

选择 0.5 秒的理由是：与目标简单方向操作的实际执行节奏相符，配置语义直观，且不必要求接近精确帧的手速；但仍能限定为一次短操作。它是结合参考资料作出的本项目设计选择，必须通过键鼠/手柄实操判断是否过宽或过紧。不能把社区经验包装成官方参数。

## 实施顺序与交付边界

第 1～4 步已落实到工作区；第 5 步的独立编译与选定纯合同测试完成，Unity 原生集成和人工验收未完成。以下步骤同时保留为后续维护约束。

### 第一步：先固定合同用例与坐标采样规则

- 对照当前 Controller、移动转换、锁定状态和 ASM 消费链路，落实坐标基准采样点及方向参考会话规则。
- 先写少量确定性的合同用例，再修改核心，避免实现中途反复改变含义。优先纯逻辑测试，不围绕私有字段/方法做反射断言。
- 规则若需要改变玩家当前操作方式，应明确指出，不把坐标转换重构变成移动/相机行为迁移。

### 第二步：补记录，同时修正有效性与消费规则

- 保留设备采集、固定步骤交接、权限/角色归属机制，补有限长度、可排序的移动历史。
- 一并调整历史保留、终端缓存与整组凭据校验；确认前面的步骤可以超过 0.2 秒，且整组仍能正确消费。
- 配置窗口与历史容量必须一致：不能静默接受实际上无法保存的长窗口，也不能无限保留记录。

### 第三步：方向识别与 State / Sequence

- 核心外解释四主方向及回中；复用移动方向转换，处理保持、抖动和参考会话变化。
- 实现当前输入 State 和纯 Event Sequence，事件保留源时间和身份。只暴露默认 0.5 秒的可调整段窗口，不先扩展逐 Clip 时限、混合 State 或嵌套条件。
- 将多事件凭据交给运行时候选，统一仲裁后消费，不写回共享 Condition，也不另建一套动作播放/调度系统。

### 第四步：编辑器与资产迁移

- 将 7 个普攻迁移为单 Event Sequence，保留其他参数、外层引用和用户编辑内容；迁移前后对照差异。
- 编辑器直接配置 Event Clip；State 明确标注当前状态，“进入方向”明确标注事件。不恢复旧检查对象层层嵌套。
- 没有实际需求时不新增突刺、挑空或蓄力技能，不改无关场景、Prefab、输入绑定、项目设置或包。
- 确认无引用后替换本轮过渡的单事件/按钮状态条件，不长期维护两套并行接口；保留仍有效的序列化引用与 GUID。

### 第五步：验证后再评价手感与稳定性

**纯合同测试重点（可用少量参数化用例覆盖）：**

- 单 Event 与多 Event；合法顺序、错误顺序、夹杂记录、重复步骤及多个候选起点。
- 整段 0.5 秒边界、修改窗口后的效果；早期步骤超过 0.2 秒仍有效，终端过期后整段拒绝。
- 同一输入更新/固定步骤内的快速后前攻击；相同时间戳的确定顺序；重复读取不复制事件。
- 保持不重复生成方向事件，回中后再次进入才有新事件，中心/方向边界抖动不误触。
- State 只检查当前；序列只检查事件；一个事件不能充当两步。
- 整组原子消费、已消费步骤不复用、松开保留、旧 owner/Tick/输入会话/方向参考会话凭据失效。

**Unity 集成与人工验收（按用户最新要求，由用户执行）：**

- 执行 ASM 集成测试，验证只有胜选候选消费、开始失败不消费、取消窗口和普通攻击回落；不是仅看纯逻辑测试。
- 键鼠及手柄，在不同相机角度、SoftLock/HardLock 下验证实际移动与招式方向一致；无锁定目标时方向招式拒绝，普通操作正常。
- 换目标、目标失效、镜头转动、目标移动、禁用/启用、失焦/恢复及切角色，不伪造新方向事件、不继承旧序列。
